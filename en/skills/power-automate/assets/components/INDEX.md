# Power Automate component catalog

Action blocks **pasteable into the designer**, one file per component, extracted from flows of reference projects and
normalized by the skill's rules (R1-R13, `Catch` with `Skipped`, `Terminate` after `Nega`, no environment literal
outside `CONFIG`, security flags on). Names, tables, procedures and connections are placeholders: `<prefixo>_...`,
`<procedure_...>`, `<tabela_...>`; sample entity **Order**, scope **Unit**.

The complete, already assembled template is `../flow-write-template.json`. The components are the **parts**; the template is
the **assembly** and is not repeated here.

## 1. How to read this catalog

Each component has `<name>.md` (explanation) and `<name>.json` (the same JSON as the `.md` block, for the verifier
and for pasting). The descriptive components (`trigger-*`) have no `.json`: the trigger is not pasteable.

- **Frequency**: how often the block (or its equivalent) repeated across the reference flows, SQL and Dataverse tracks and
  the inbound flow: `very common` (almost every flow), `common`, `occasional` (a few flows) or `rare` (a single flow).
- **Maturity**:
  - `stable`: appears in a flow pasted and **returned by the designer** (baseline) or in an inbound flow in
    production, and repeats in more than one flow.
  - `unique`: confirmed, but in a single flow (does not generalize on its own).
  - `designed`: generated by script from the project and **with no proof in the designer**; marked `[unverified]`.
  A `stable` component may carry adjustments marked `[unverified]` in its own file (what changed relative to the baseline).
- **Connections**: `<prefixo>_sharedsql`, `<prefixo>_sharedoffice365users`... are example logical names of the connection
  reference (the environment pattern is `<prefixo>_shared<connector>_<suffix>`); the logical name of **your** environment applies (skill `power-platform`).

## 3. Assembly order

### 3.1 Flow called by the app (SQL track; swap 4 and 9 on the Dataverse track)

In the root scope (`Escopo_<flow>`), after the trigger:

1. [`trigger-power-apps-v2`](./trigger-power-apps-v2.md): typed by hand (positional parameters)
2. [`config`](./config.md): `Bloco_config`
3. [`identify-caller`](./identify-caller.md): `Bloco_chamador`
4. [`read-caller-sql`](./read-caller-sql.md): creates `Try_pedido` (or `read-caller-dataverse`)
5. [`action-switch`](./action-switch.md): inside the `Try`; one `Caso_<acao>` per action

Inside each `Caso_<acao>`, in this order:

6. [`authorize-by-flag`](./authorize-by-flag.md): first node of the case (no `runAfter`)
7. [`normalize-input`](./normalize-input.md): or `screen-filters-json` in an export; `derive-value-switch` if there is a derived value
8. [`state-before`](./state-before.md): only in an action on an existing record
9. [`unit-scope`](./unit-scope.md): or `dataverse-units-scope`
10. [`validate-with-message`](./validate-with-message.md)
11. [`audit-trail`](./audit-trail.md): optional; only in an edit with history
12. [`if-nothing-changed`](./if-nothing-changed.md): optional; with the trail, point it to `Bloco_trilha`
13. [`write-via-procedure`](./write-via-procedure.md): or `dataverse-compensation` (Dataverse) or `support-email-with-partial` (external effect)
14. [`translate-code-and-respond`](./translate-code-and-respond.md): last node of the case

After the `Try`:

15. [`connector-catch`](./connector-catch.md): outside the `Try`, its sibling
16. [`run-log`](./run-log.md): optional in a flow called by the app (see the `Terminate` pitfall)

The ready-made assembly, with a single case, is the template `../flow-write-template.json`.

### 3.2 HTTP inbound flow

1. [`trigger-http-inbound`](./trigger-http-inbound.md): typed by hand; plus the two root variables
2. [`token-cache-and-http-response`](./token-cache-and-http-response.md): `Escopo_Principal` with `Scope_Token` and the two responses
3. [`inbound-config`](./inbound-config.md): inside the main scope

## 4. Common pasting rules

1. **Paste from top to bottom**, in the order of section 3. The `runAfter` of each envelope's root points to the previous node
   of the assembly order; check the name and adjust it to your flow.
2. **First node of a branch** (`Caso_`, `Yes`, `No`) has no `runAfter`: delete the `runAfter` key of the root node before
   pasting. The verifier reads the snippet as a fragment because the root has `runAfter`; without it, references to
   actions outside become errors.
3. **Names are unique across the whole flow** (F004). Each component uses the suffix `_gravar`; change it to the action's suffix
   (`_excluir`...) in every occurrence, including inside `outputs('...')` and `body('...')`.
4. **Connections**: each envelope carries `allConnectionData` with one entry per connector action (R1). The `<prefixo>_shared...`
   is the logical name of the **target environment's** connection reference; never copy the one from another environment.
5. **Expected verifier warnings**: `F006` (the referenced action is outside the pasted snippet: `CONFIG`, `Chamador`,
   `Normalizar_gravar`...) and, in two components, `F009` (scope without `Skipped` on purpose). Each file lists its own.
6. **Scope envelope**: a single-action block becomes a `Scope` by wrapping it; the scope is transparent at run time and costs
   one indentation level in the designer (`../../references/clipboard-format.md` §2).
7. **Trigger and root variables** (`Initialize variable`) are typed by hand.
8. After pasting and saving, **return** what the designer returned to the project baseline (read-only file); what
   the designer normalizes is a new rule (`../../references/designer-baseline.md`).

## 5. What was left out

| Block | Why |
|---|---|
| Office Script / Excel (barcode, spreadsheet) | No reference flow calls an Office Script: the script existed as a "plan B" and the final design generates the HTML inside the flow. Not used at run time |
| Fixed-width identifier (e.g. barcode) in WDL | Depends on a fixed input length; stays in `html-to-pdf` only as a note |
| Loose `Select`, `Filter array` (`Query`), `Compose` | They appear in almost every component (mapping, index, trail, CSV); on their own they are a trivial designer action |
| `Apply to each` with concurrency | Absorbed by `batch-upsert-changeset` (`chunk` + `concurrency`); outside the batch, the `Foreach` with a counter is a trivial action |
| Variables (`Initialize/Increment/Append`) | `Initialize` only works at the root and is typed by hand (`trigger-http-inbound`); `Increment/Append` are inside the batch |
| Pagination by `Do_until` + skiptoken | Old design; the native one (`native-pagination`) replaces it |
| User notification via Teams | Does not appear in any of the reference flows |
| 429 retry on the `InvokeHttp` connector | `[unverified]`: how the policy appears in the designer JSON; stays as a pitfall in `batch-upsert-changeset` |

## 6. How to validate

```text
python en/skills/power-automate/scripts/verificar-fluxo.py en/skills/power-automate/assets/components/<file>.json
python -m pytest tests/_i18n/test_power_automate_en.py -q -p no:cacheprovider
python tools/lint_skills.py en/skills/power-automate
```

Destination: terminal, from the repository root. The test `tests/_i18n/test_power_automate_en.py` runs the verifier over
**every** `.json` in this folder and requires `0 error(s)`; it checks that the JSON of each `.md` block equals the `.json`
next to it and that every component is in this index.
