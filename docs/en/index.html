How it works

You don't need to know the method.

The kit carries the method for you. Four ideas make the path easy, even for someone who has never gathered requirements or built a Power App.

1

One command per stage

Ten stages, from /pp-en:new to /pp-en:publish. Each one checks that the previous one is done. Ran one out of order? It tells you which one to run instead.

2

A fresh session per stage

Everything a stage produces is saved to disk, so the next one starts with a clean context. Every stage ends with the Next step block: the command and a reminder to type /clear first.

3

You only stop where a person is needed

Approving the MVP, the identity and the prototype; creating tables, pasting screens and flows, running user acceptance and publishing. Everything else is produced and validated for you.

4

Who thinks is not who executes

The session defines the request and judges; the agents write and prove what they did. Every delivery gets a verdict (accepted, revision or escalated to you) before it reaches you.

Lost the thread? /pp-en:progress shows at any time where the project stands and the next command. The state lives in STATE.md, at the project root.

Open Claude Code in an empty folder and type /pp-en:new followed by your idea. Then follow the Next step block at the end of each stage. 🔴 person marks what only someone in the environment can do; Claude shows a numbered walkthrough and waits.

Prototype not approved

The adjustment requests go to prototype-adjustments.md and the next step is /pp-en:design again. Mockups and prototype redo only what changed.

Test or acceptance failed

Each failure goes to fixes.md, tagged as app or flows. The next step is /pp-en:build app or /pp-en:build flows, and then the test again.

Stopped midway?

Run the same command again. The stage resumes from what's on disk, and /pp-en:progress always knows where you are.

After publishing

Send the list of changes with /pp-en:change. Each request becomes a spec, the agents work in parallel, QA runs and user acceptance reopens for a new version.

Who thinks and who executes

Each stage's session is the head: it writes each agent's request, runs the validator again and gives a verdict per delivery: accepted, revision (the same agent, with a sharper request, two at most) or escalated (comes to you). Before showing the design sample or the prototype, Claude takes screenshots of the screens and looks at them. Since thinking and judging is the small part of the work, the head can use a stronger model and the hands a faster one. You pick the profile in /pp-en:new.

Existing app

Already have an app? Just describe the problem.

Outside the pipeline, the power-platform orchestrator routes a plain-language request to the right mode.

You sayWhat Claude does
“The KPI doesn't match the gallery”Investigate mode. Walks screen → formula → source → flow → procedure → data, one hypothesis at a time, and proves the root cause before proposing code.
“A user sees another unit's data”Checks the layer that actually blocks access: flow + procedure on SQL, security roles on Dataverse. The screen only filters.
“Audit the whole app”Reviewers in parallel by discipline (UX, development, performance, data, flows, SQL) and a second check of the strongest findings.
“Add a status filter here”Goes straight to powerapps-canvas, without the full protocol.
A list of changes to an app published by the kit/pp-en:change: one spec per request, agents in parallel, judgment, the change's QA and user acceptance reopened.
“Promote to UAT/PROD”Solutions, environment variables, connection references and the pac CLI; what goes by pasting and what goes by solution.
“Is it ready?”Runs the final gate: every validator that applies, plus the checklist.

What's included

Ready-to-paste pieces and validators that run.

Five domain skills behind the stage commands: power-platform, powerapps-canvas, power-automate, sql-procedures and dataverse.

25

Canvas components

Ready-to-paste YAML, with the variables each one expects in OnStart.

  • side menu (fixed, collapsible or drawer), top menu, home screen with cards
  • table gallery, sorting, cursor pagination, KPI card
  • modals, loading overlay, toast, empty state, no-access panel
34

Power Automate blocks

Clipboard JSON plus notes, with the assembly order for each kind of flow.

  • identify and authorize the caller, scope by unit
  • write via stored procedure, translate code and respond
  • $batch upsert on Dataverse, CSV export, run log
✓

Runnable validators

Python, standard library only. ✅ requires evidence: command, output and date.

  • validar-telas.py for screens
  • verificar-fluxo.py for flows
  • lint-procedure.py for procedures
  • verificar-prototipo.py for the prototype
One data track per project: SQL Server or Dataverse.
The real name wins. Formulas and flows use the names read from the environment, never the ones from the plan.
Writes always go through a flow, with a 4-field response and .Run() inside IfError.
The flow reads the caller's identity from its own context and authorizes each action.
No environment literals in deliverables: environment variables and connection references instead.
A generator never overwrites what was pasted. What's generated goes to dist/.

Install

Two commands, then /pp-en:new.

Inside Claude Code, add the marketplace and install the plugin. Type /pp-en: to see the stage commands; if they don't show up in a session that was already open, restart Claude Code.
